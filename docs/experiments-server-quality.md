# サーバ側で品質を上げられるか — 実測

> **結論: 3DGS はこのプロジェクトで採用しない（2026-09-07 決定）。**
>
> サーバ側で計算資源を増やしても品質が上がらないことが実測で確認され、
> 構成を iPad 完結に切り替えた。関連コード（COLMAP 書き出し・初期点群・
> ポーズ精密化・station 抽出・splat ビューア）は削除済み。
> 以下はその判断に至る実験の記録として残す。

2026-08-26 / 対象 `room-c57d5e3a`（408 フレーム / 撮影 104 秒）/ MacBook Pro M1 Max

PM から「3DGS によるサーバ側の高精度化が欲しい」との要望を受けて行った実験の記録。

**結論を先に書く。計算資源を増やす 2 つの施策は空振り、データの整合性を直す
施策が当たった。** 入力が矛盾していれば、計算を増やしても矛盾を精密に再現するだけ。

| 施策 | 数値 | 目視（盲検） |
|---|---|---|
| 解像度 480 → 1920 | ±0.18 dB（反復分散と同程度） | **区別できず** |
| ガウシアン 50万 → 100万 | +0.44 dB | **区別できず** |
| **露出補正** | **+1.23 dB / ムラ −10%** | **有意に良い** |

## 1. 実験の設計

### シーンを 1 回だけ生成して全条件で共有した

ICP 精密化後のポーズ、初期点群、評価用に除外するフレーム、入力画像 408 枚が
全条件で同一。**変えたのは `--max-resolution` と `--max-splats` の 2 引数だけ。**
前処理を条件ごとに回すと、差が前処理由来か解像度由来か切り分けられなくなる。

### 実行順をシャッフルした

低い順に流すと、熱による減速が解像度の効果に化ける。シードを固定して
シャッフルし、記録した。

### 同一条件を 2 回ずつ回した

**条件内の分散を知らないと、条件間の差が有意か判定できない。**
640 / 1280 / 1920 の 3 条件で 2 本ずつ走らせた。

### 評価は共通解像度に揃えた

Brush が出す PSNR は各自の学習解像度での値で、低解像度で学習したものほど
高く出る。描画結果と正解画像の両方を 960×720 に揃えてから測った。

## 2. 解像度は効かない

13 条件（7 解像度 × 50万、3 解像度 × 100万、反復 3 本）を回した。

| 解像度 | PSNR | SSIM |
|---|---|---|
| 480 | 25.04 | **0.8903** |
| 640 | 25.08 / 25.11 | 0.8901 |
| 800 | 25.08 | 0.8889 |
| 960 | **25.18** | 0.8887 |
| 1280 | 25.01 / 25.08 | 0.8860 |
| 1440 | 25.06 | 0.8849 |
| 1920 | 25.00 / 25.13 | **0.8814** |

**単調な傾向がない。** 最高は 960、最低は 1920。反復による分散は 0.03〜0.13 dB で、
解像度による差（幅 0.18 dB）と同程度。有意差はない。
SSIM はむしろ解像度を上げると単調に悪化している。

**盲検でも 13 個すべてを区別できなかった。**

### 理由: 入力画像に 480 を超える情報がない

| 縮小先 | 原寸に対する PSNR |
|---|---|
| **480** | **39.2 dB** |
| 640 | 41.2 dB |
| 960 | 44.5 dB |

480 まで落として戻しても 39 dB。**1920×1440 で保存していても中身は 480 相当。**

原因は手ブレ。ポーズから直接計算できる。

```
露光      1/100 秒（固定）
焦点距離  1623 px
角速度    中央値 25.4°/s（上位 10% で 46.3°/s）

回転由来のブレ 7.2 px + 並進由来 2.2 px = 約 10 px
→ 実効解像度 約 200 px 相当
```

**1 枚の露光中にカメラが 10 画素ぶん動いている。**
3DGS は入力にない情報を作れない。

## 3. ガウシアン数も目視では効かない

| 解像度 | 50万 | 100万 | 差 |
|---|---|---|---|
| 640 | 25.08 | 25.52 | +0.44 |
| 960 | 25.18 | 25.55 | +0.37 |
| 1920 | 25.07 | 25.53 | +0.46 |

3 解像度すべてで一貫して改善し、分散の 3〜15 倍。**数値としては本物。**
しかし盲検では区別できなかった。ファイルは 112MB → 225MB になる。

## 4. 露出補正が当たった

### 症状

平坦面（壁・床）の誤差の **76% が低周波**。これがムラの実体で、
15 画素スケールの分散には出てこない。

評価 9 枚それぞれの全体オフセット:

```
-1.2  +5.5  -0.9  +1.6  +3.4  +11.9  -0.5  +1.3  -8.7
幅 20.7 レベル / 標準偏差 5.3
```

**同じ壁がフレームによって 20 レベル違う明るさで写っている。**
ARKit の自動露出が ISO を 160〜1600 の間で動かしており、窓を向いたか
壁を向いたかで反応している。

**解像度やガウシアン数をいくら変えてもムラは動かない**（5.9〜6.5 で一定）。

### 解き方

同じ 3 次元点を見ている全フレームで、その点が同じ色になるゲインを解く。
詳細は `recon/mdr2colmap/photometric.py`。

求まったゲインは **EXIF の ISO と相関 0.92**。カメラが実際に行った露出補正を
復元していることが確認できる。

### 結果

| | 補正なし | 補正あり |
|---|---|---|
| ムラ | 6.45 | **5.82** |
| 露出ずれ σ | 5.62 | **3.22** |
| PSNR | 25.08 | **26.31** |
| SSIM | 0.8901 | **0.8967** |
| 白飛び | 2.15% | **1.69%** |
| 入力の整合性 | — | **−42%** |

**盲検で 2 回とも補正版が選ばれた。位置を入れ替えても結果が変わらない。**

所要時間は +29 秒（前処理 17.0s → 45.2s）。学習時間は変わらない。

## 5. 犯した誤りの記録

同じ失敗を繰り返さないために残す。**5 回の誤りのうち 4 回は測定・実装の欠陥**で、
一度は誤った結論に到達しかけた。

| | 誤り | 発見の経緯 |
|---|---|---|
| 1 | 補正の向きが逆（掛け算 / 割り算） | 学習前検証で −79.8% の悪化として発覚 |
| 2 | sRGB 空間で適用（リニア光であるべき） | 同上 |
| 3 | 暗くする方向のみで階調喪失（255→148） | テクスチャに縞が出て発覚 |
| 4 | **ビューア 2 枚並べで GPU 競合** | ユーザが 2 回とも「先に開いた方」を選び発覚 |
| 5 | 3DGS 学習時間 262 秒（再現せず、実際は 317 秒） | 4 回測り直して発覚 |

**4 番目が最も重大だった。** ウィンドウを 2 つ並べると同じ GPU を奪い合い、
後から開いた方の描画が劣化する。これにより一度「露出補正は効果なし」と
誤って結論づけた。**同一ウィンドウ内で Tab 切り替え**する方式に変えて、
正しい判定が取れた（`tour/Sources/TourRenderer.swift`）。

**指標も 2 度作り直した。** 「中間スケールの変動」は不適切だった。露出補正は
カメラの自動露出を打ち消すので、本来の陰影（窓際は明るく、隅は暗い）が
復元される。変動が増えるのは正しい挙動で、継ぎ目とは無関係。
継ぎ目は不連続な段差、真の陰影はなだらか — この区別ができる指標が要る。

## 6. 次に効くのは撮影側

サーバ側の計算資源では、これ以上は伸びない。律速は撮影品質にある。

| 施策 | 期待 | コスト |
|---|---|---|
| **ブレたフレームを捨てる** | アプリ記録の sharpness は 25〜3547 と 140 倍ばらついている | **ほぼゼロ** |
| パンを半分の速度に（25°/s → 12°/s） | ブレ 10px → 5px、実効解像度が倍 | 撮影時間が倍 |
| station 位置で 1〜2 秒静止する | ブレゼロの基準フレームが得られる | 手順の変更 |

**1 つ目が最も費用対効果が高い。** 実装はキーフレーム採用条件の閾値を
上げるだけで、撮影時間も処理時間も増えない。

## 7. この実験の適用範囲

**1 部屋のみで検証した。** 白い壁と什器が主体の部屋なので、木目・畳・布のような
高周波テクスチャが多い部屋では違う結果が出る可能性がある。ただし
「入力に 480 を超える情報がない」ことがブレ由来である以上、撮影方法が同じなら
部屋を変えても同じ制約がかかるはず。

## 付記: RoomPlan 同居の実測（2026-09-07）

間取り図の生成源として RoomPlan を使うにあたり、**MDR 撮影と同じ `ARSession` で
同時に走らせられるか**を実測した。

iOS 17 で `RoomCaptureSession(arSession:)` が追加されており、自前のセッションを
渡せる。`RoomPlanCapture.swift` の「差し込めない」というコメントは iOS 16 時代の
記述で古かった。

| | RoomPlan なし | あり＋深度再適用 |
|---|---|---|
| 採用フレーム | 160 枚 | **166 枚** |
| 映像 | 1920×1440 | 1920×1440 |
| メッシュ頂点 | 21,622 | 21,741 |
| メモリ | 498 MB | 553 MB |
| 発熱 | nominal | nominal |
| RoomPlan | — | 壁 4 / 物体 3 |

**劣化しない。** 懸念していた採用フレームの減少も発熱も起きなかった。

### 深度が落ちる罠

`RoomCaptureSession.run(configuration:)` は共有セッションを**自前の設定で上書きし、
`frameSemantics` から `.sceneDepth` を落とす**。深度付きフレームが 0 枚になり
MDR が成立しなくなる。

**しかも挙動が一貫しない。** 計測順を「なし→あり」にすると深度が有効に見え、
「あり→なし」にすると無効になった。競合状態がある。

1 回目の順序だけで判断していたら「同居できる」と誤って結論し、撮影経路を
作り直した後に**間欠的な不具合**として現れていた。順序を入れ替えて測ったから
見つかった。

対処は起動 2 秒後に深度だけ再適用する（`RoomScan.reapplyDepth`）。
`resetTracking` は付けない（RoomPlan の状態を壊す）。実測で 836/881 枚 = 95% が
深度付きになり、欠けるのは冒頭 1.5 秒だけ。**RoomPlan を撮影開始前から回す**
ことでその空白を隠している。

### 座標系の一致

同一セッションなので座標が一致する。実測（`room-33d49373`）:

```
床の高さ   メッシュ -1.621   RoomPlan -1.654   差 3.4cm
平面の範囲 メッシュ X -2.49〜+0.97  Z -0.58〜+3.21
          RoomPlan X -2.23〜+0.96  Z -0.54〜+3.10
```

**位置合わせが要らない。** 間取り図上の位置から該当 station へ飛ぶような連動が
そのまま作れる。別セッションで 2 回撮る方式ではこれが失われる。
