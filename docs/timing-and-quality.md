# 所要時間と品質の実測

最終更新 2026-08-24 / 計測環境 iPad Pro 11" 2020 (A12Z, LiDAR) + MacBook Pro M1 Max

本番の部屋を実際に撮影して計測した値のみを載せる。推定値には「未計測」と明記する。
数値がどのスキャンで測ったものかを併記する。同じ設定でも部屋が違えば時間は変わる。

基準スキャン: **`room-c57d5e3a`** / 408 フレーム / 撮影 104 秒 / 230 MB

## 1. 要約

**3D モデルは 2 種類あり、用途が違う。**

| | **iPad 単体** | **Mac で高精細化** |
|---|---|---|
| 撮影から完成まで | **約 3 分** | **約 7 分**（+ 転送時間） |
| 形式 | テクスチャ付きメッシュ (GLB / USDZ) | 3D Gaussian Splatting (PLY) |
| 見た目 | 部屋と認識できる。輪郭が甘い | 写真に近い |
| 閲覧 | iPad の Quick Look でその場で | 専用ビューア (madoriba tour) |
| 用途 | 現地での即時確認、寸法・間取り | 営業資料としての内見体験 |

現地で撮った直後に iPad で確認でき、写実的なモデルは Mac に持ち帰って作る、
という二段構えになっている。

## 2. 時間の内訳

| 段階 | 実測 | 備考 |
|---|---|---|
| 撮影（iPad） | **104 秒** | 408 フレーム / 230 MB |
| iPad でのモデル生成 | **79 秒** † | UV 展開 + テクスチャ焼き込み + 書き出し |
| — **ここまでで iPad 単体モデルが完成** | **183 秒** | |
| 転送（iPad → Mac、230 MB） | **未計測** | Files アプリ経由の手動コピー |
| ポーズ精密化 (ICP) | 10.1 秒 | 残差 8.3 → 4.4 mm |
| COLMAP 形式への変換 | 0.03 秒 | 408 カメラ |
| LiDAR 初期点群の生成 | 7.8 秒 | 424,010 点 |
| 視点 (station) 抽出 | 0.02 秒 | 10 箇所 |
| **3DGS 学習 10,000 iteration** | **300 秒** | |
| — **ここまでで高精細モデルが完成** | **422 秒** | 転送時間を除く |

† iPad の生成時間はひとつ前のスキャンでの実測。今回のスキャンでは記録していない。
メッシュ規模がほぼ同じ（面数 179,015 → 179,022）なので同等とみなせる。

**サーバ処理（転送後）は 318 秒。** 要件の 5 分（300 秒）を 18 秒超過するが、
許容範囲として合意済み。

撮影を含めない理由は、5 分要件が「アップロードから完了まで」を対象にしているため。

### 3DGS 学習の時間は部屋によって変わる

| スキャン | フレーム | 3DGS 学習 |
|---|---|---|
| room-c57d5e3a | 408 | 300 秒 |
| ひとつ前 | 469 | 317 ± 1 秒（4 回計測） |

**当初 262 秒と記録していたが再現しなかった。** 後日、同一シーン
（`images.bin` のハッシュまで一致）・GPU 排他・AC 電源で 4 回測ったところ
317 ± 1 秒だった。262 秒を説明できる外的要因は見つかっていない。
以後は 317 秒を採用している。

## 3. 各モデルの中身

| | iPad 単体（メッシュ） | Mac 高精細（3DGS） |
|---|---|---|
| 構成要素 | 179,022 面 | 500,000 ガウシアン |
| テクスチャ | 2253×2253 JPEG アトラス 1 枚 | なし（各ガウシアンが色を持つ） |
| ファイル | GLB 6 MB / USDZ 14 MB | PLY 112 MB |
| 再現精度 (PSNR) | 約 16 dB ‡ | 約 22.5 dB ‡ |

‡ PSNR はひとつ前のスキャンでの実測。今回のスキャンでは評価画像を出していない。

**PSNR の差 6.5 dB は、目視でもはっきり分かる差。**
メッシュ側は形状の誤差（数 mm〜1 cm）にテクスチャを貼り付けるため、
家具の輪郭や細い部材でテクスチャが引き伸ばされる。
3DGS のガウシアンはメッシュに縛られないので、この制約を受けない。

## 4. なぜこの設定なのか

### 学習解像度は 640 に固定

| 学習解像度 | 3DGS 学習 | PSNR |
|---|---|---|
| **640（採用）** | **317 秒** | 22.53 |
| 960 | 333 秒 § | 22.75 |
| 1920 | 712 秒 § | 22.95 |

§ 960 と 1920 は別セッションでの計測で、再計測していない。640 の値が
262 → 317 秒に修正されたため、**同じずれが乗っている可能性がある。**

960 は +0.21 dB のために、1920 はさらに +0.20 dB のために時間を使う。
費用対効果が急速に悪化するので、**引数で変更できないようにしてある。**
高解像度への対応は、要件を緩めるか処理環境を変えるかの判断とセットになるため、
後付けの課題として切り離している。

### テクスチャは解像度を上げても改善しない

アトラスを 2048² → 4096² にしても PSNR は 16.04 → 16.03 で変わらなかった。
ポーズ誤差を 64% 削っても、形状誤差を 20% 改善しても、3 回とも効果ゼロだった。

**テクスチャの品質は貼る先の形状精度で頭打ちになる。**
iPad 単体モデルをこれ以上良くするには、解像度ではなく形状を直す必要がある。

## 5. 既知の不具合

### 3DGS の学習が確率的に落ちる

Brush が依存する burn の融合エンジン (burn-fusion) に競合状態がある。

```
burn_cubecl_fusion::engine::launch::output.rs:207
  called `Option::unwrap()` on a `None` value
```

**同一シーン・同一引数で落ちたり通ったりする。** 実測では room-c57d5e3a の
1 回目が 54 秒で落ち、2 回目が 300 秒で完走した。ガウシアン数の上限やシーンとは
相関しない（ひとつ前のスキャンで 50 万が 4 連続成功した後、
別シーンの 50 万で落ちた）。再現条件は掴めていない。

burn 側に修正はなく、公開されている回避策は融合の無効化のみ
([tracel-ai/burn#4347](https://github.com/Tracel-AI/burn/issues/4347))。
融合は Brush のバックエンド型そのものに埋め込まれているため、
機能フラグでは外せない。

**対処: 最大 3 回のリトライを入れた**（`pipeline.py` の `TRAIN_ATTEMPTS`）。
落ちるのは学習の序盤なので、捨てる時間は 1 分弱。失敗は PLY が出ないことで
確実に検知できる。1 回落ちた場合の合計は 372 秒になる。

### 保存済みバンドルから焼き直せない

iPad のテクスチャ焼き込みは録画停止時にしか走らない。使っているのは
メモリ上の `ARMeshAnchor` と GPU テクスチャで、セッション終了時に破棄される。
バンドルには `mesh.ply` と `frames/` が残っているので後から導線を足すことは
できるが、現状は**撮り直すしかない。**

## 6. 現状の制約

PM 判断が必要な項目。

| 項目 | 状態 |
|---|---|
| **転送** | 手動。Files アプリで iPad から Mac へコピーしている。自動化は未実装 |
| **サーバ** | 開発機の MacBook Pro をそのまま使っている。同時に 1 件しか処理できない |
| **対応範囲** | 単一の部屋のみ。複数部屋の統合は未実装 |
| **中断・復帰** | 撮影中の着信、メモリ逼迫、バックグラウンド遷移での挙動が未確認 |
| **撮影ガイダンス** | 未取得領域の可視化は ARKit のワイヤーフレーム表示で代用中 |
| **iOS 側のテスト** | なし。実機で動かして目視するしか検証手段がない |

Mac 側の変換処理には 18 件の自動テストがある。

## 7. 計測の再現手順

```bash
# iPad 単体モデル: アプリ内で録画を停止すると自動で生成され、所要時間が表示される

# Mac 高精細モデル
mdr2colmap server room-xxxx.mdr -o scene/ \
  --brush vendor/brush/target/release/brush
```

段階ごとの所要秒数が表で出力される。

**GPU を使う計測は必ず排他で行うこと。** 過去に、ビューアや別の学習と同時に
走らせたために 34 分の処理を 103 分と誤計測した例がある。
